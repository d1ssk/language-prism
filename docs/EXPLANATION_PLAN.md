3. 10組程度を目安に、必要な本文・既存の読み・解説だけを一度取り出し、日英の解説を直接作成する。出力上限があれば保存を分割してよいが、そのたびに調査・検証・報告の工程を一周させない。
4. 執筆中に本文との対応と日英の情報対応を確認する。独立した全文読み返しは必須にしない。実際に照合できたものをまとめて `checked` にし、未確認のものだけ `written` に残す。保存後は不具合・疑義・差分のある箇所だけを読む。
5. 文の説明に不可欠で確信のない事項だけ調査する。既知の語彙・文法の毎回の検索、参考資料の一律追加、読みの全面再校閲はしない。確かな内容で十分説明できる場合は不要な専門論点を省く。本文等の改善候補は一行で記録して続行する。
6. 記事完了時と実際の引き継ぎ時だけ、台帳の単独検査と短い進捗更新を行う。通常の応答区切りでは台帳への一括記録で足りる。残り全体が終わったら未確認項目・解説に影響する疑義・例外・機械検査の失敗箇所を処理し、6検証と最終記録をまとめて行う。既存の確認済み解説を全件再読する工程は設けない。

本文・`ttsText`・音声・識別子・順序を保持する。修正が必要な疑いは本書の課題欄に分けて記録する。解説の編集に伴う読みの補足・関連メタデータの更新は可能だが、読み本体は別途検討する。音声生成・コミット・push・deployは実行しない。

## 台帳と再開手順

`docs/explanation-progress.json` に全言語エントリーを記録する。`pending` は未着手、`written` は執筆済み、`checked` はAIによる本文との照合・日英の内容確認済みを表す。専門家校閲を意味せず、公開データの `translation.reviewStatus` は変更しない。`noEquivalent` の確認は独立したレコードに記録する。

```sh
# 再開時はstatusを1回。statusも保持対象を検査するためverifyの連続実行は不要。
node --import tsx scripts/content/explanation-progress.ts status
# 実際に確認したキーをまとめて渡す。以下は構文例であり、確認前には実行しない。
node --import tsx scripts/content/explanation-progress.ts mark checked random-1/u026/ja random-1/u026/en
# 執筆済みだが内容確認が残る場合のみwrittenを使う。
node --import tsx scripts/content/explanation-progress.ts mark written random-1/u026/es
# 記事完了・実際の引き継ぎ時にまとめて実行する。
node --import tsx scripts/content/explanation-progress.ts verify
```

件数だけでは品質を証明できない。`checked` は、執筆中を含め、本文と両言語の解説を実際に照合できたものに付ける。スクリプトの成功や生成した事実だけで付けない。標準より少ない項目には `--reason` で理由を記す。確認後に解説を修正した場合は変更箇所を確認してハッシュを更新する。`mark` 自体が保持対象・構造等を検査するため、その前後で毎回 `status` / `verify` を重ねない。`verify` は言語的な正しさを自動認定しない。全体完了時の `verify --complete` は未着手・未確認が残らないことも要求する。
