## 今回承認された変更

- **分量は直近の `u020`〜`u025` 程度でよい。短くしない。** 通常は語彙3・文法2・補足1を日英で書き、文中の意味・形・働き・使い方を説明する。短い定型句は水増しせず、長文は必要な説明を加える。
- 高速化の対象は、同じ文章の繰り返し取得、独立した全文再読、毎回の検索、表示確認、検証、報告の反復。説明の中身や対象件数を減らして速度を出すのではない。
- 台帳の確認済み項目は再生成・短縮・全面校正しない。以前のブラウザ確認や6検証を追体験しない。

## 再開時に一度だけ行うこと

1. `AGENTS.md` と本書を読む。範囲・品質の詳細が必要なら `EXPLANATION_PLAN.md` の該当節だけを参照する。`VALIDATION.md` の履歴、古い作業ログ、過去の一時原稿は読み直さない。
2. `node --import tsx scripts/content/explanation-progress.ts status` を一度実行する。これは保持対象も検査するので、直後に `verify` を重ねない。
3. 次の未整備ブロックのID、本文、既存の読み・必要な解説を一度抽出する。形式に迷う場合だけ、確認済みの解説を1〜2件参照する。記事JSON全体や音声・翻訳属性を毎回チャットに出力しない。
4. 新しい計画・全件調査・代表例作成・検証基盤構築を始めず、そのまま次の未整備項目から執筆する。

## 生成・保存のループ

1. **10組程度を目安**に複数の本文をまとめて読み、解説を直接生成する。これは厳密な上限・下限ではない。出力制限に合わせて5組程度へ分割しても、保存のたびに調査・検証・報告を挟まない。全言語分を同じ手順で扱う。
2. 執筆しながら、引用した語句が本文にあるか、語形・構文・指示対象の説明が合うか、日英で同じ情報を述べているかを確認する。事前の言語別長文メモと完成原稿を二重に生成しない。
3. 既存形式で `vocabulary`・`grammar`・`notes` を保存する。必要な場合だけ `pronunciation.note`・`references` を編集する。本文・`ttsText`・`pronunciation.text`・音声参照・翻訳属性・ID・順序・公開状態は変更しない。
4. 原文と照合できた項目をまとめて `mark checked` にする。執筆済みでも照合できていないものは `written` にする。生成や自動検査だけを内容確認と呼ばない。項目数が少ない短文には `--reason` で理由を残す。
5. **保存した全文を再出力して読み返す工程は設けない。** エラー・疑義・修正箇所だけを確認して、次のブロックへ進む。生成し直しによる文体統一・追加の磨き込みを繰り返さない。

`mark` は複数キーを受け取り、保持対象・構造等も検査する。一件ずつ実行したり、同じブロックに `written`→`checked`→`status`→`verify` を必ず重ねたりする必要はない。

```sh
# 構文例。実際に内容を確認したキーだけをまとめて渡す。
node --import tsx scripts/content/explanation-progress.ts mark checked random-1/u035/ja random-1/u035/en
```

前の作業の簡単な適用ヘルパーは `.cache/public/explanation-work/apply-batch.py` にある。存在すれば再利用できる。入力は `practical/random-1/u035/ja` 等をキーにしたJSONで、`text` に既存本文、`v` に `[term, ja, en]`、`g` に `[point, ja, en]`、`n` に `[ja, en]` の配列を渡す。任意の `pn` は読みの補足、`refs` は資料の追加。本文の一致を確認して解説欄だけを書き換える。使用前に実装を一度確認する。

`.cache` は無視対象の一時領域で、別環境では存在しない場合がある。その場合も短い保存処理で足り、汎用ツールの開発は不要。**古い `batch-*`・`next-*` 原稿は保存済みのJSONと違うことがあるので再適用しない。** `u034` まで保存・台帳反映済みで、未適用原稿から再開する必要はない。正本は `content/public` と台帳。言語一覧・順序は `config/languages.json` を使い、Libraryの追加原語も落とさない。

## 調査の上限を設ける

- 既知の語彙・文法を毎回検索しない。資料リンクを全件に付ける作業もしない。
- 本文を説明するうえで必要で、確信が持てない事項に限って調べる。説明に不要な専門論点・例外を自分から増やさない。確かな説明で十分ならその範囲を使う。
- 複数箇所の疑義はまとめ、該当箇所だけに対処する。必要な不確実性を無視したり、出典を創作したりしない。
- 本文の改訳候補、既存の読み・音声の改善候補は `EXPLANATION_PLAN.md` の課題欄に短く記録する。今回の範囲外の再校閲・音声生成へ広げず、解説を正しく書ける他の項目は進める。
- アラビア語・中国語の発音補足は文固有のものだけ。既存の読み本体を保持し、一般規則・凡例は学習ガイドに任せる。全読みを改めて調査し直さない。

## 検証・報告の頻度

- **生成中のブラウザ、スクリーンショット、表示確認、音声生成は行わない。** ローカルサーバーを起動する必要もない。
- **6検証は残り全体の仕上げ時に一度。** 各バッチ・記事・通常ターンの終了時には実行しない。
- 台帳の単独 `verify` は記事完了時、ユーザーによる停止などの実際の引き継ぎ時、全体完了時に行う。通常のgoal継続のターン区切りだけでは実行しない。
- 本書の現在地は記事完了時か実際の中断時に短く更新する。バッチごとに `VALIDATION.md` を増やさない。再開位置は台帳から分かるため、履歴の文章量を増やさない。
- ユーザーへの進捗連絡は簡潔にし、連絡のために再検証や全件集計を走らせない。
- 全体の仕上げでは `written`、解説に影響する未解決事項、例外、検査失敗に集中する。確認済み全件の第二巡の読み返しはしない。

最後に以下を順に実行し、結果を `VALIDATION.md` に一度まとめる。`npm test` がpublic/localの作業領域を更新するため、並行ビルドはしない。失敗した場合は原因を修正し、影響する検査だけ再実行する。

```sh
node --import tsx scripts/content/explanation-progress.ts verify --complete
npm run check
npm run validate:content
npm test
npm run build:public
npm run build:local
npm run privacy:check
```
