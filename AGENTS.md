# Development rules

- Site title is `language prism`. Preserve existing data formats.
- `config/languages.json` is the single source of truth for ja, en, es, fr, de, ru, ar, zh, ko in that order; UI, validation and Python TTS read it.
- UI locales are ja/en under `src/pages/[locale]/`; copy belongs in `src/i18n/ja.ts` and `en.ts`. Keep UI locales distinct from the nine content languages. Share content/media across both UI locales and preserve base paths and same-page language switches.
- Keep display `text` separate from `ttsText`. Japanese TTS must use reviewed hiragana input, never fall back to kanji display text.
- Raw private content, media and voices belong outside the repository. Public builds must never read private roots or `.env.local`. Use only explicit public content and referenced media; reject symlinks and path traversal.
- Public staging/output/cache and local staging/output/cache are separate. `npm run build` is always public. Never broaden the Pages upload beyond `dist/public`.
- Do not modify `_misc/voice_test` or the linked `d1ssk.github.io` site. Reuse the working TTS virtual environment and model cache without reinstalling them.
- Audio generation is an independent offline command, never a build step. Mock outputs must remain under an ignored test directory and must not be published.
- Run `npm run check`, `npm run validate:content`, `npm test`, `npm run build:public`, `npm run build:local`, and `npm run privacy:check` for relevant changes. For the explanation-only enrichment task below, run this suite once at completion of the full remaining scope, not after each batch, article, or turn. Documentation-only handoff updates do not require this suite.
- Do not commit, push, or deploy without explicit user instruction. Keep secrets, reference voices and machine-specific paths out of tracked files.
- Arabic and Chinese explanations start with `pronunciation` before vocabulary/grammar. Ready entries require `arabic-romanization` for ar (learner-oriented MSA Latin transcription; ā/ī/ū, ḥ/ṣ/ḍ/ṭ/ẓ, ʿ/ʾ, sh/kh/th/dh/gh; explain gender, liaison and pausal choices) and `pinyin` for zh (tone-marked Standard Mandarin, underlying tones, neutral tones unmarked, explain sandhi). Keep this display-only reading separate from `text` and `ttsText`; follow docs/CONTENT_FORMAT.md.
- Pronunciation notes contain only sentence-specific observations (e.g. actual sandhi, gender variants, or pausal forms in that sentence). Do not repeat general transcription conventions, symbol legends, underlying-tone policy or neutral-tone notation under readings. Chinese reading headings are `拼音` / `Pinyin`.
- Shared pronunciation conventions, symbol legends and general references belong in the bilingual public study guide (`/ja/guide/`, `/en/guide/`), linked from the home page. Do not repeat these references in each sentence; retain sentence-specific grammar references where relevant.

# Explanation enrichment: user-approved fast workflow (2026-10-27)

- Start with `docs/EXPLANATION_HANDOFF.md`. It contains the resume point and execution procedure; `docs/EXPLANATION_PLAN.md` defines scope and editorial quality. `docs/VALIDATION.md` is historical evidence, not a checklist to repeat. Do not reread the historical logs to resume.
- Preserve all previously completed explanations. Continue from the ledger's pending entries; at the 2026-10-28 handoff, 333 entries are checked and the next entry is `random-1/u035`. Do not restart, shorten, or re-review completed entries.
- The user accepts the current explanation length, including `random-1/u020`–`u025`. Maintain this detail and bilingual coverage. Speed comes from reducing process overhead, not reducing explanation quality or scope.
- Read each source block once and compose the explanations directly in batches. Aim for 10 units per batch where output limits permit; save smaller chunks if needed without restarting the surrounding workflow. Reuse the existing format and simple application helpers; do not build new review infrastructure.
- Check source correspondence and Japanese/English consistency during composition. A separate full reread, printing generated explanations back into the chat, and repeated polish passes are not required. Inspect only failed, uncertain, or changed portions. Mark `checked` only after an actual content check; generation or passing a script alone is not evidence of that check.
- Do not routinely browse for familiar vocabulary or grammar, add references for every entry, or expand into specialist side questions. Use clear, well-supported explanations; investigate only uncertainty essential to explaining the actual sentence. Log nonblocking source-text or pronunciation concerns once and continue with other entries. Never invent facts or citations to avoid research.
- Do not run browsers, screenshots, visual QA, audio generation, or the six-command suite during explanation batches. Update the ledger in batches; its `mark` command already checks protected content and structure, so do not automatically surround every mark with `status` and `verify`. Run standalone ledger verification at article completion, actual handoff, and final completion, not every normal turn.
- Keep progress notes short. Update the handoff at article boundaries or actual interruption, and the validation report at final completion; do not append a report for every few units. Final content review is limited to remaining `written` entries, flagged issues affecting explanations, exceptions, and detected failures; do not reread every completed explanation again.
- Preserve all existing privacy, format, TTS, media, and publication boundaries. Never reset the ledger baseline or mark unfinished entries complete to speed up progress. No commit, push, or deployment without explicit instruction.
